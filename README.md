score-based testing framework for testing and scoring agent tasks.

to use pats, put `pats.yaml` in your project root. see [`pats.example.yaml`](./pats.example.yaml) for an example of such a configuration. 

`pats.yaml` is a mapping of vectors. each top-level key is a vector's id, and a vector has a `kind` (`sandbox`, `agent`, `task`, `scorer` or `suite`), optional `defaults`, and non-empty `items` keyed by id. an item inherits every default it doesn't set and overrides whole fields; an explicit null (`collect: ~`) unsets one, and an empty item (`curl:`) inherits everything. a task is a single scenario given to the model under test. a scorer runs on the output of an agent run and scores one aspect of it, 0.0 - 1.0. ids are the primary way to refer to things, and they double as human-readable names: one namespace per kind, holding that kind's vectors and items, where an id names a set of items (a vector its items, an item itself) and must name exactly one set -- so a vector may share its id with its sole item, a task and a scorer may share an id, but a task vector `smoke` next to an unrelated task `smoke` is an error. no `/`, `$` or whitespace in ids. defaults are per-item templates: `${task}` / `${agent}` / `${scorer}` / `${sandbox}` expand to the item's id in that kind's fields and `${vector}` to its vector's id, everywhere except inline content -- a literal prompt, an inline script, `env` (any other `${x}` is a load error; inside a flow mapping `{...}` quote the value, else the `}` closes the mapping, and spell an empty item `a: ~`). to share defaults between vectors use a yaml anchor: `defaults: &x {...}` in one, `defaults: *x` or `defaults: {<<: *x, timeout: 5m}` in another.

a task's prompt is one of `prompt` (the literal text), `prompt-file` (a file to read) or `prompt-cmd` (a command whose stdout is the prompt; it runs after `stage`, so it can look at the staged workdir). the fields that run something -- a task's `stage` and `collect`, a scorer's `score` -- each take one of two forms. the plain key is an inline script: a body starting with `#!` runs as an executable (its shebang picks the interpreter), one without runs under `/bin/sh -e`, and `${...}` in it is the shell's, not a pats template. the `-cmd` key (`stage-cmd`, `collect-cmd`, `score-cmd`) is a command line, exec'd directly with no shell: the value is tokenised into argv (posix-sh quoting, but no `$`-expansion, globbing, or pipes), a first word containing a `/` is a file resolved from the directory of the file it's written in, and a bare first word is looked up on `PATH`. every host script gets `<pats root>/bin/` prepended to its `PATH`, so shared helpers go there and are called by name. an item sets at most one key of each of these slots, and in `defaults` a slot merges as a unit -- setting any key of it replaces the whole slot. host scripts run in the directory of the file their item was defined in: the pats root for `pats.yaml`, the task's own directory for a `task.yaml` (below). they get these env vars: `PATS_ROOT` (the config dir, absolute), `PATS_*_ID` (`PATS_TASK_ID`, `PATS_AGENT_ID`, and for scorers `PATS_SCORER_ID`), `PATS_MODEL`, `PATS_AGENT_HARNESS`, `PATS_TASK_DIR` (the directory the task was defined in, absolute), `PATS_OUTPUT_DIR` (this pair's `<run>/<agent>/<task>`), `PATS_RUN_DIR` (the run dir holding every pair's output) and `PATS_RUN_ID` (its basename, e.g. `003-20260621-fluffy-bunny` -- the agent in the sandbox gets this one too); a task's scripts additionally get `PATS_WORKDIR`, `PATS_AGENT_HOME` and the task's own `env:` (a mapping of variable names to values; it merges key by key over defaults, and names may not start with `PATS_` or be `PATH`). scorers don't get a workdir -- they read the collected output dir. `PATS_AGENT_HOME` is the host side of the agent's sandbox `HOME`, created (with the harness creds already copied in) before `stage` runs, so `stage` can seed harness config there -- e.g. a `~/.claude/settings.json` with hooks, or a codex `config.toml`. copy real files, not symlinks into the host tree, which don't resolve in the sandbox. it lives until the pair is done, so `collect` can read back what the agent left in it. both are host paths: inside the sandbox the workdir is mounted at `/workspace` (the agent's cwd) and the agent home at `/pats-home` (its `$HOME`), so a seeded file that must hold an absolute path -- a git remote url, say -- uses those. a task can also set `prepare` / `prepare-cmd`: it runs inside the sandbox, as root, after `stage` and before the agent -- spread's prepare, for system state the agent needs (packages, services, users). its script (or the `-cmd`'s file) and the pats root's `bin/` are pushed to `/pats-prepare`, run with `bin/` first on `PATH` and the workdir as cwd, then removed before the agent starts, since the agent can read everything else. it gets the task's `env:` and `PATS_TASK_ID`, `PATS_AGENT_ID`, `PATS_AGENT_HARNESS`, `PATS_MODEL`, `PATS_RUN_ID`, `PATS_WORKDIR` (`/workspace`) and `PATS_AGENT_HOME` (`/pats-home`) -- no host paths -- and runs under the sandbox's egress policy, so anything secret belongs in `stage`. what it leaves in the workdir and home is handed to the agent user. the task `timeout` covers the agent only; bringing the sandbox up and preparing it has its own ten-minute budget. a failed `stage`, start or `prepare` is the pair's error, named in its `metadata.json`, with the step's output in `stage.log` / `prepare.log` in the pair dir.

a task vector can take `dir: <path>` instead of `items`, to keep each task in a directory of its own. every directory under that path holding a `task.yaml` is one task, at any depth; its id is the directory's name, and `task.yaml` holds the same fields as an inline task. directories starting with `.` are skipped, and a `task.yaml` below another task's directory is an error. a `dir` vector takes only `kind` and `dir` -- each task is configured by its own `task.yaml`, nothing is inherited from `pats.yaml`. its scripts run in its directory, so they reach their own fixtures by plain relative paths:

```yaml
# pats.yaml
knockout:
  kind: task
  dir: cases/knockout
```

```yaml
# cases/knockout/curl/task.yaml
env:
  BRANCH: ubuntu-26.04
prompt: |
  author a slice for the package `curl`.
stage: prepare-knockout         # bin/prepare-knockout, found on PATH
collect-cmd: ./collect.sh       # next to this task.yaml
```

an `agent` runs a harness -- an agent cli that runs the agentic loop in a sandbox. `harness:` picks one of four, each baking in the cli and how it authenticates. `opencode-openrouter` is the `opencode` cli with models served via openrouter (reads `OPENROUTER_API_KEY` from the env; write the model without the `openrouter/` prefix, it's added for you). `claude-cli-keyless` is the `claude` cli, keyless: your oauth creds (`~/.claude/.credentials.json`) are copied into the sandbox, and the model is a raw anthropic id. `codex-cli-keyless` is the `codex` cli, keyless: your chatgpt login (`~/.codex/auth.json`) is copied into an isolated `CODEX_HOME`, and the model is a raw openai id -- a codex login kept only in the os keyring has no file to copy, so switch codex to file credential storage first. `copilot-cli-keyless` is the `copilot` cli, keyless: a github token read from `COPILOT_GITHUB_TOKEN` in the env (an ambient `GH_TOKEN`/`GITHUB_TOKEN` is deliberately not forwarded), and the model is a copilot model id (e.g. `claude-sonnet-4.5`, `gpt-5`) -- copilot's default login lives in the os keychain, so mint the token first: macos `security find-generic-password -s copilot-cli -w`, or `gh auth token`. an agent can set `effort:` -- reasoning effort, mapped to claude's `--effort` (low|medium|high), codex's `model_reasoning_effort`, copilot's `--effort` (none|minimal|low|medium|high|xhigh|max), and opencode's `--variant` (provider-specific, e.g. high|max|minimal) respectively. all four harnesses log a machine-readable event stream to `stdout.log` (claude: stream-json; codex: `--json`; copilot: `--output-format json`; opencode: `--format json --thinking`), which feeds the live tool counter and the cost/token summary in each pair's `metadata.json` -- keyless codex and copilot are billed against the subscription, so they report tokens but no per-run dollar cost (copilot additionally records its premium-request count). every agent can run tasks; an agent you don't list in any suite simply never runs as one -- which is how you keep a stronger model around purely to score a weaker one (it must then be some scorer's `agent`, else it's flagged as an orphan). scorers come in two flavours, told apart by their fields. a script scorer sets `score` (inline) or `score-cmd`; a script's shebang picks the interpreter and deps (e.g. `#!/usr/bin/env -S uv run --script` with inline pep-723 deps -- trampoline to python/spacy/whatever you like). it exits 0 and prints a float in `[0,1]` on its first stdout line, or `na` to skip (a non-zero exit is a failure). a uniform layout is one vector default, `score-cmd: scorers/${scorer}.sh`. an inline `score` runs from a temp file, so a python scorer importing a module next to it should use `score-cmd` instead. the other flavour sets `agent:` and one of `prompt` / `prompt-file` / `prompt-cmd` (ask that agent to judge) -- **not implemented yet**; configuring one is rejected at config validation until it lands.

finally, suites select what runs. a suite is a named (`agents`, `tasks`, `scorers`) triple, and both cross-products are implied within it: `pats run` runs its `agents` x `tasks`, `pats score` scores its `tasks` x `scorers`. each axis takes a scalar or a list of ids of that kind, vector or item, and a vector id expands to its items -- `tasks: [slicer, frobnicator]` is every task in the `slicer` vector plus one stray. a suite vector takes `defaults` like any other (`defaults: {agents: all}` once, instead of on every suite). `scorers` may be empty (a run-only suite). every agent, task, and scorer must land in at least one suite (agents referenced by a scorer's `agent` are exempt), so forgetting to wire a new item in is a load-time error rather than a silent coverage hole. suites may overlap (a `smoke` suite inside a `full` one) -- duplicate pairs are deduped, not errors; an item named twice within one axis is. scores aggregate as plain means (per pair over its scorers, then per agent over its tasks). narrow a run or score with `-S <id>` (a suite or a suite vector), `-a` and `-t` (agents / tasks, or their vectors), and a score also with `-s` (scorers, or their vectors). lowercase short flags name the item kinds, uppercase the suites that group them. the filters intersect, and one that matches nothing in the selected suites is an error. a narrowed score merges into the run's `scores.json`, replacing only the cells it recomputed, so rescoring one fixed scorer keeps everything else.

there are three (and a half) stages of a pats workflow. `pats init` makes every image your suites' sandboxes need -- pulls the published sandbox and egress proxy, builds `build:` and `base:` / `provision:` images, provisions lxd layers -- and pins each by id in `.pats/images.json`. it is the slow step, run when you say so: after cloning, after changing a sandbox, after upgrading pats. it takes `run`'s selectors (`-S`, `-a`, `-t`) plus `--sandbox <id>` and `--driver <d>`, and `--force` rebuilds and re-pulls what exists. `pats run` never builds or pulls: it starts every sandbox from its pinned image, and stops before the first pair, naming the `pats init` that fixes it, when a sandbox is not pinned, its image is gone, or the pin was made against another docker daemon or lxd remote than the one answering now. then `pats run` runs your suites -- your agents across their tasks -- and saves the result to `.pats/runs/<run_number>-<date_slug>-<friendly-name>/` (e.g. `003-20260701-jacquard-runner`; the two words are generated from the numeric prefix) -- that usually takes a hot moment. then `pats score` scores the most recent run, or you can ofc instruct it to test an older run too. note that this is not intended as a way to keep old historic runs and therefore, if you change the scorers and rerun on the old run, you *are* going to just run the new scorers. finally, if you have any agentic scorers they are not run by default, but only with `--agentic` flag (note: agent scorers aren't implemented yet, so `--agentic` currently has nothing to run).

agents are always run in a sandbox -- we never run without one. each agent names the sandbox it wants via `sandbox: <id>` (if only one sandbox is defined, it's the default). a sandbox has a `driver` (`docker`, the default; `podman`; `lxd`; or `bwrap`) and, under a container driver, at most one of `image` or `build`. with neither, it runs the published pats sandbox -- an ubuntu-based fat image carrying all the harness clis, at the versions this pats release pins in `images/harness-versions` -- pinned to your pats version (`ghcr.io/lczyk/pats/sandbox:v<version>`); `image: <ref>` runs any other image instead (`ghcr.io/lczyk/pats/sandbox:latest` follows the newest stable release). alternatively `build: <path>` names a docker build context (a dir with a Dockerfile, or a Dockerfile path, relative to `pats.yaml`) that `pats init` builds -- an unchanged context reuses the image it built before, and the built image id is recorded in each pair's `metadata.json`. the cache key covers the context and the id of every `FROM` image: a base you refresh with `docker pull` triggers a rebuild, and an absent base is pulled first, but pats never pulls one that is present. the build gets the pinned pats sandbox as a build arg, so a dockerfile that extends it writes `ARG PATS_SANDBOX` / `FROM ${PATS_SANDBOX}` and tracks the pats it runs under. one guard: if the build context contains `.pats/` (run artifacts) and the dockerfile reads the context (a `COPY`/`ADD` not sourced `--from` another stage), the effective `.dockerignore` must exclude it (a literal `.pats/` line) or the run refuses to start -- pats won't bake your run history into the image, and won't edit ignore files for you. a context-less dockerfile (no `COPY`/`ADD`) needs no ignore file. `bwrap` (linux-only) is not implemented yet and is rejected at validation; `container` works anywhere docker does (incl. macos, where docker is itself a linux vm).

any sandbox can make its image from `base` and `provision` / `provision-cmd` instead: the provision step runs once per image, as root, on top of `base` (the pats sandbox when `base` is empty), with the pats root's `bin/` first on its `PATH`; docker and podman compile the two into a generated dockerfile on the same cache as `build:`, and the next `pats init` rebuilds the image when the script, `bin/` or the base changes. `limits: {cpu, memory, disk}` caps a sandbox's resources (`disk` is lxd-only) and `max-parallel` caps how many of its pairs run at once, whatever `-j` says.

`driver: lxd` runs the agent in an lxd system container, or a virtual machine with `vm: true`, on the server an `lxc` remote names (`remote:`; the cli's default remote when omitted) -- a real system with systemd and snapd, a vm boundary for untrusted runs, no docker. pats drives it through the `lxc` cli in an lxd project `pats` it creates on first use (a restricted client certificate gets the admin command to run once). the image is provisioned on the server and cached there as `pats-img-<key>`: with no `base`, the pats sandbox's tools on `ubuntu:26.04` first (the same `images/provision-sandbox.sh` the docker image is built with), then the sandbox's own `provision` on top. each pair gets a fresh instance; the workdir and the agent home go in as tar over exec and come back after the agent, so the server needs no shared filesystem. the agent runs as a `pats` user, never root, and may `sudo` only with `sudo: true` on the sandbox (a task can override it). `profiles:` (in the `pats` project) and `config:` pass through, but an instance whose expanded config carries a nic pats did not give it, or any `raw.*` key, is refused. egress works as under docker: `none` is no nic at all; open is a bridge of the pair's own with nat and an acl dropping private, local and multicast ranges (so not the server's lan; the one host service it still reaches is lxd's own dns and dhcp on that bridge, which lxd lets through ahead of any acl); a proxy policy puts the agent alone with its proxy container on a bridge with no host address, the proxy reaching out through the shared `patsup` bridge. a server that also runs docker drops traffic on bridges docker was not told about; preflight catches that and prints the fix an admin applies once: either the two `iptables -I DOCKER-USER` lines for `patsbr+` and `patsup`, or, with docker 28 or later, `net.ipv4.ip_forward=1` set before docker starts (a `/etc/sysctl.d` file), which keeps docker's FORWARD policy at accept. the lxd acls still fence each bridge either way. `PATS_LXD_UPLINK` names an existing bridge (e.g. `lxdbr0`) for image builders to use meanwhile. `-j auto` sizes by the server's cpus. `pats clean` sweeps runs whose lease lapsed (each run holds one on the server while it lives); it reads a lease's time against its own clock, so the machine running it and the ones running pats should keep their clocks within a few minutes of each other (ntp is plenty). `docs/spec/lxd.md` is the design.

a sandbox can also declare an `egress` policy. absent, the network is open, and open means unfiltered: the internet, but also the host itself, its lan and a cloud host's metadata endpoint. for the internet without those, write `egress: {default: allow}`, a proxy whose dial guard refuses private, loopback, link-local, multicast and carrier-grade nat targets -- though a host or lan on global addresses still passes. `egress: none` is no network at all (`--network none`; an agent cannot run there, since every harness reaches an inference api, and the loader says so). a mapping runs a filtering proxy sidecar on an internal network: the sandbox has no route out except through it. `default: deny` (the default) makes `allow` an allowlist; `default: allow` makes `deny` a denylist; both lists apply either way and a deny match always wins. an entry is a host (`github.com`), a suffix (`.ubuntu.com`), a host with a port (`github.com:22`; without one, 80 and 443), an ip, or a url entry: a host plus a path glob (`github.com/*/some-answer-repo*`, `*` matches anything) or a go regexp (`'api.github.com ~^/repos/[^/]+/x$'`, over the path and query). a url entry terminates tls for its host with a per-run CA the sandbox is told to trust, so each request is filtered by full url -- an `allow` url entry matches the path exactly, a `deny` one case-insensitively, each erring toward closed; a `..` in the path does not dodge an entry. every other host is a tunnel the proxy never decrypts, and the tunnel holds the client to its word: the tls hello must name the CONNECT host, so a shared front end cannot be reached under a name the policy never saw. targets on private, loopback, link-local, multicast or carrier-grade nat (`100.64.0.0/10`) addresses are refused unless `allow-private: true`. `deny-response` picks what a refused request sees: `403` (the default), `404`, `reset`, or `timeout` (held 60 seconds, then reset). the proxy audits every request as one json line into the pair's `egress.log` (an `open` and a `close` per tunnel with the bytes each way, a `req` per request it can see into, each naming the entry that decided it), and refusals land in the run metadata in three lists: `denied_egress` is what no rule anticipated -- the agent reached for something nobody planned for, a built-in cheat detector -- `blocked_egress` is what the policy names (an explicit `deny`, a path no `allow` url entry admits, a private target, a tls hello naming another host), and `failed_egress` is upstream trouble (a dial failure, a certificate whose stapled ocsp response says revoked). the first two are warned about at the end of each pair. `metadata.json` also records the effective policy, the sidecar image id and the bytes moved. under an allowlisting proxy, the hosts the harness itself needs -- the inference api, token refresh, opencode's startup fetches -- are merged in automatically per harness, so the config only lists what the *task* needs (e.g. apt mirrors). preflight proves the topology before the first pair: with the proxy env unset, a direct connection out of the sandbox has to fail, or the run refuses to start. `image` overrides the sidecar image (docker and podman). `methods: [GET, HEAD]` is a posture against writes: an unlisted method is refused on every host the policy allows, which makes the proxy inspect (mitm) every allowed host but the harness's own; an `allow` entry that names its method (`POST api.github.com/graphql`) overrides it, a `deny` one (`PUT,PATCH github.com/*`) scopes the deny. a task can set `egress: {allow, deny}` too: its entries are unioned over its sandbox's for that task's pairs, the sandbox keeps every other field, and pairing such a task with an agent whose sandbox runs no proxy is a load error. rules every task of a vector shares are sandbox posture and belong on the sandbox; the task level is for the per-task bit -- the one answer repo, the one extra package index. in `defaults` the block is replaced whole, like any field, and `egress: ~` drops it. `docs/egress.md` is the reference, including running the proxy on its own (`pats egress run`) and the `pats egress check | suggest | log` tools.

## installation

pats is a single go binary. you need go 1.26+ to build it, and docker to run the sandboxes.

this is the 1.x line, released as `1.0.0-beta.N` pre-releases from the `1.x` branch until 1.0. `main` carries 0.x, and `@latest` resolves to it until 1.0 ships, so name the beta explicitly. 1.x reads a different `pats.yaml` shape from 0.x (see [`pats.example.yaml`](./pats.example.yaml)).

put it on your PATH with `go install`:

```sh
go install github.com/lczyk/pats/cmd/pats@v1.0.0-beta.5    # installs into $(go env GOBIN)
```

or run it without installing at all:

```sh
go run github.com/lczyk/pats/cmd/pats@v1.0.0-beta.5 run
go run github.com/lczyk/pats/cmd/pats@v1.0.0-beta.5 score
```

from a clone, `make install` builds the binary (upx-compressed if `upx` is on PATH) and symlinks it into `~/.local/bin`:

```sh
git clone -b 1.x https://github.com/lczyk/pats && cd pats
make install
```

### published images

pats publishes two images per release, both tagged `v<version>` and pinned by the binary of that version: the default sandbox (`ghcr.io/lczyk/pats/sandbox`, used by a sandbox that names no `image` or `build`) and the egress proxy (`ghcr.io/lczyk/pats/egress-proxy`, the sidecar behind an `egress:` block -- the pats binary itself, started as `pats egress run`). `:latest` on both follows the newest stable release. a released install's `pats init` pulls them from ghcr. the version is the module tag for a module install, else the `VERSION` file of the checkout; `pats --version` shows it. so a clone build pins to the images of the release its tree is based on, whether or not the tree has moved on -- build the images locally and pats finds those instead of pulling:

```sh
make images          # the sandbox, tagged :v<version>, :latest and :26.04 for the host arch
make egress-image    # the proxy, tagged :latest and :v<version>
```

## examples

typical loop -- make the images once, run the suites, then score them:

```sh
pats init                # pull / build every sandbox's images and pin them in .pats/images.json
pats run                 # run all agent x task pairs, save to .pats/runs/<n>-<date>-<adj>-<noun>/
pats score               # score the latest run (tasks x scorers)
```

narrowing and parallelism:

```sh
pats run -a haiku-claude-cli -t simple                  # just one pair
pats run -t write-readme                                # every task in that vector
pats run -S readme                                      # just one suite
pats run -j-1                                           # parallel pairs, auto job count
pats score -s style -a haiku-claude-cli                 # one scorer vector on one agent
pats score -r jacquard-runner                           # score an older run by its friendly name
pats score -r .pats/runs/003-20260701-jacquard-runner   # ... or by path
```

all commands take `-c <path>` to point at a `pats.yaml` other than the one in the cwd.

### example config

the model under test is `claude-haiku-4-5`, run two ways: through the `claude` cli (`claude-cli-keyless`) and through `opencode` over openrouter (`opencode-openrouter`). running the same model under two harnesses isolates the harness's effect from the model's.

it has one task vector, `write-readme`, with 3 tasks: `simple`, `hard`, `monorepo`. the vector's defaults name the prompt file and scripts once (`prompt-file: prompts/${vector}-${task}.txt`, `stage-cmd: scripts/stage.sh --${task}`) and each task is just its id. judging by those, these tasks seem to be testing some behaviour related to readme authorship. they may be about testing the model itself, but also could be testing some skill or instruction given to the model.

there are 4 scorers in the `style` vector: `only-ascii`, `title-correct`, `no-finite-verbs` and `no-colloquialisms`. former 2 scorers are implemented in a purely imperative manner. `only-ascii` deducts 0.1 form the score for each occurrence of excessive whitespace. `title-correct` is much closer to a binary yes/no question so it could simply output 1.0/0.0 respectively. latter 2 scorers are more _"fuzzy"_. `no-finite-verbs` scorer uses [`spacy`](https://pypi.org/project/spacy/) -- a python NLP library. `no-colloquialisms` is agentic, and therefore nondeterministic: it uses an agent to score the results (commented out in the example until agent scorers are implemented). there is, in fact, one more agent defined for that purpose -- `judge`, a `claude-cli-keyless` agent running `sonnet`. it's left out of every suite, so it never runs as a task -- it only scores, letting us judge a weaker model (`haiku`) with a stronger one (`sonnet`).
